# 清理协议

本协议把桌面清理器常见的“规则、扫描、执行、恢复”模型转换为宿主 Agent 可审计的流程。适用于缓存、应用残留、启动项、服务、计划任务、浏览器外部宿主、右键菜单、文件关联和 Appx 等清理请求。

## 模式与边界

按以下顺序推进，不跳过中间阶段：

1. `inventory`：只读枚举和分类，确认机器、用户、权限、路径与管理策略。
2. `analyze/preview`：解析已审查的规则，生成具体文件、注册表项、服务或任务的命中清单，不改变状态。
3. `apply`：用户确认清单后逐项执行，范围扩大或证据变化就暂停并重新计划。
4. `verify`：用相同范围复扫，核对目标消失/状态变化、空间差异和相邻功能。
5. `restore`：按备份批次恢复，恢复后再次复扫并报告无法恢复的项。

“清理”“优化”“一键处理”都不等于授权。定时任务或无人值守调用默认只允许 `inventory` 和 `analyze/preview`；不要从其他清理器继承静默删除、自动关机或“保存上次选择即执行”的行为。清理器保存的“自定义清理记忆”只是下次预览的默认勾选草案，仍要重新 `analyze/preview` 并重新确认。

同一时间只推进一个 `apply` 或 `restore` 批次。开始前取得独占批次锁，记录批次 ID；并发清理与并发恢复会让备份归属和复核结果无法对应。

## Finding 与规则模型

每个命中项都应至少保留：

- `id`、类别、用户可读名称、实际影响和技术位置；
- 证据来源（显示名、Publisher、产品/版本、签名、安装目录、命令、注册表/任务 XML、哈希）及采样时间；
- 动作类型：`report-only`、删除值、删除键、移动到隔离、禁用服务/任务、启动官方卸载器；
- 风险、是否需要管理员权限、是否可批量选择、警告与明确排除理由；
- 预览时的路径/大小/哈希或原状态，以及备份路径、执行结果、退出码和复核结果。

规则应分开描述：检测条件（OR 命中即可）、正向目标、排除项、默认是否选中、警告、动作、回滚和验证。没有正向目标或只有宽泛通配符的规则不进入执行阶段。

动作分级不得升级：启动项、服务、计划任务、右键扩展分别对应“删除该入口”“禁用服务”“禁用任务”“禁用扩展”，不能因为同属一个厂商就升级为卸载整个软件。只有进程证据、没有持久化入口时只报告，不强杀进程——守护进程会重启，且容易误伤用户正在使用的主程序。

用户可以维护本机白名单。白名单项仍然展示原始证据和技术位置，但不参与批量勾选和批量执行；不要用白名单掩盖证据，也不要让白名单静默扩大到同厂商的其他项。

## 分析阶段

- 只解析具体且可追溯的规则；对每个目标展开环境变量和通配符，列出字面绝对路径、类型、大小、时间、所有者和来源规则。
- 不跟随 junction、symlink 或其他 reparse point；锁定、拒绝访问、已消失或哈希变化的项目标记为 `skipped`，不要用强制句柄或重试掩盖问题。
- 区分注册表“值”和“键树”，区分“文件移动到隔离”与“永久删除”，区分“禁用”与“删除”。浏览器 profile、凭据、邮件/聊天数据库、同步根目录和主程序默认仅报告。
- 显示命中数量、总字节、预计权限、警告、排除数量和无法确认的项目。证据不足或多个厂商强证据冲突时只能 `report-only`，不能靠 GUID、哈希、PID、系统宿主名或路径子串单独认定归属。
- 单个位置拒绝访问、注册表项受保护或路径消失时记录警告并继续枚举，不要让一个位置的失败终止整次盘点；缺失的覆盖范围要写进报告。
- 未解析出组件路径时结论只能是 `unknown`，不能据此判定“文件缺失/注册残留”。只有路径已明确、且该路径确实不存在时才作为残留提示。
- “弹窗”“广告”“守护”这类行为标签描述现象，不构成厂商身份证据。行为标签只能提高审查优先级，不能替代身份确认，也不能拼进用户可见的厂商名。
- 正常且组件完整的第三方集成（压缩、对比、编辑器等右键项）只进入库存清单，不进入风险清单；库存视图用于显示/隐藏和溯源，风险视图只放需要提示或处理的项。
- “表观大小”不等于“可回收空间”。硬链接、reflink/CoW 克隆和稀疏文件会让多个路径共享同一批块，删除其中一个路径回收不到对应字节；统计前先按设备号和 inode 去重，并把共享块的情况写进预览。

## 执行与批次

用户确认时引用固定的 finding ID 和目标列表。对每一项：

1. 重新检查目标存在、路径未越界、大小/哈希或原状态未改变。
2. 先备份：注册表导出，文件移动到回收站/隔离目录，服务保存启动类型与状态，计划任务保存 XML 与启用状态。
3. 备份文件可读取后才执行单项动作；失败时保留原状并记录原因。
4. 执行后立即复核该项，记录退出码、动作时间、恢复位置和新状态。

打开厂商卸载器前重新读取同一个卸载注册表项，确认产品名称、发布者和卸载命令三项与预览时完全一致；任何一项缺失或变化就拒绝执行并要求重新扫描。卸载器只负责打开厂商界面，由用户在界面内确认，不代替用户点击、不追加静默或强制参数。

清空回收站和“把删除项暂存到回收站”属于互斥动作。同一批次不得既依赖回收站回滚又清空回收站；确实需要清空时先确认没有未验证的清理批次依赖它，并使用系统提供的清空能力，不要直接删除 `$Recycle.Bin` 内容。

以普通权限完成盘点和预览。只有写入 HKLM、服务、系统级计划任务或所有用户范围的项才请求提权，并且只提升已批准的单项动作。用户取消提权或没有管理员凭据时继续以普通权限扫描和导出报告。提权后重新扫描并恢复勾选，但必须重新确认，不得自动继续执行提权前的选择；不使用服务、计划任务、注册表劫持、UAC 绕过或永久修改 ACL 实现静默提权。

每批次写入独立清单，至少包含 `created_at`、主机/用户标识的最小必要部分、规则来源、批准范围、逐项 before/after、backup、status、verification 和 rollback。清单不得包含密码、Cookie、令牌、私钥或完整用户目录。

## 验证与恢复

清理完成后重跑原始规则和相邻功能检查。仍命中的项、动作返回成功但状态未变的项、锁定项和被策略重新创建的项必须保留在结果中。恢复时拒绝越出本批次备份根目录的路径；目标已有同名文件时不覆盖，报告人工合并。

批次恢复部分失败时，成功项与失败项分别记录：失败项保留在批次中并可单独重试，不能因为整批标记完成而丢弃，也不能在恢复未通过验证前删除备份。删除任何备份前先确认对应目标已恢复并复核通过。

## 来源与参考

以下项目仅作为行为与安全边界参考，不复制其代码或运行时。括号内是本 Skill 最近一次只读复核的上游版本：

- RogueCleaner（v2.0.16，2026-09-09 复核）：<https://github.com/aakk007/RogueCleaner>
- FluentCleaner（26.08.03 及 Classic 1.16.206，2026-09-09 复核）：<https://github.com/builtbybel/FluentCleaner>
- WindowsCleaner（6.3.3，2026-09-09 复核）：<https://github.com/darkmatter2048/WindowsCleaner>
- WxCleaner（跨平台版本，2026-09-09 复核）：<https://github.com/yqxie1991/WxCleaner>
- disk-raccoon（c44ef19，2026-09-09 复核）：<https://github.com/orange2ai/disk-raccoon>

RogueCleaner 的多信号身份确认、清理前备份/清理后复扫/恢复批次和“未知只提示”原则适合迁移；其较新版本补充的边界同样适合迁移：注册表备份失败即取消删除、核心右键动词与系统命令只提示、正常第三方右键项只进库存不进风险、单个位置拒绝访问不终止整次扫描、行为标签不冒充厂商身份、恢复批次保留可单独重试的失败项、以及“普通权限扫描 + 单项提权 + 提权后重新确认”的权限模型。

FluentCleaner 的规则解析、检测与清理分离、排除项、Dry Run、可插拔数据库和 CLI 可观测性适合迁移；其 Inspector 展示的“本地打开规则库、汇总递归/警告/重复规则、对比两个版本”思路适合作为规则更新前的审查方式。FluentCleaner 的静默自动清理与自动关机不属于本 Skill 的默认能力。

WindowsCleaner 作为反面边界：按扩展名递归遍历整个系统盘删除 `*.log`/`*.tmp`、直接删除 `$Recycle.Bin` 内容、以及把上次自定义勾选记忆成下次可直接执行的选择，这三类行为都不进入本 Skill 的执行阶段。

WxCleaner 的“按大小分组 → 前缀哈希 → 全量 SHA-256”三级去重和跨平台回收站删除适合迁移，`windows-application-cleanup`、`macos-application-cleanup` 和 `linux-application-cleanup` 都按此执行。它在 Linux 上刻意不提供默认数据路径，这条同样保留：Linux 侧的应用数据根必须从运行进程、包文件清单和用户配置实际发现，不从 Windows 或 macOS 布局推断。

disk-raccoon 是一个同形态的 macOS 缓存清理 Skill，其“缓存地图”里经实测的相邻目录边界已并入 `macos-application-cleanup`：可删的 `Service Worker` 与同级不可删的 `IndexedDB`、Telegram 的 `postbox/media` 与 `postbox/db`、飞书的 `profile_explorer` 与 `profile_main`/`sdk_storage`，以及“微信等沙盒应用优先走 App 内存储管理入口”。它记录的两条反面做法不采纳：用脚本运行时绕过宿主对删除命令的护栏，以及把 `kill -9` 当作清理前置步骤——两者都已写入 `safety-policy.md` 的拒绝项。
